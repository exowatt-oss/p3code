# Thread artifacts

A thread's artifacts are the durable index of what it **produced** (outputs: files it changed, previews it opened, pull requests it is linked to, user attachments) and what it **consulted** (sources: files it read, pages it fetched, web searches, MCP tools, skills, subagents). Every harness contributes through one shape, `ArtifactRef` in `packages/contracts/src/threadArtifacts.ts`, so clients never scrape driver-specific tool payloads.

## Why a projection and not a client-side scan

Tool payloads are slimmed before they cross the wire (`apps/server/src/orchestration/ActivityPayloadProjection.ts` strips URLs and results) and long threads carry thousands of activities. Deriving the index once on the server, per event, keeps thread detail reads O(artifacts) instead of O(activities), and gives MCP agents (`thread_artifacts`, `thread_summaries.artifactCounts`) the same view as the UI. `payload.refs` is the one field of a tool payload the slimmer never touches: it is small, typed, and the sanctioned channel.

## Data flow

1. **Adapters emit `refs`** on tool `item.started` / `item.updated` / `item.completed` payloads by calling `extractArtifactRefs` from `@t3tools/shared/threadArtifacts` against their native tool shape. ACP computes refs once in `makeToolCallState` and carries them on `AcpToolCallState`.
2. **Ingestion** copies `refs` onto the persisted `tool.*` activity payload (`ProviderRuntimeIngestion.ts`).
3. **`projection.thread-artifacts`** (`ProjectionPipeline.ts`) consumes `thread.activity-appended` (`tool.started` registers sources only; `tool.completed` registers everything unless the call failed), `thread.turn-diff-completed` (checkpoint files → `file-output`, origin `system`), `thread.pull-request-linked/unlinked`, `thread.artifact-*`, `thread.reverted`, and `thread.deleted`. It runs last so a revert can consult the surviving turns. Bootstrap replays from sequence 0, which is how existing threads backfill: for activities without `refs`, the same extractor recognizes the legacy `data` shapes.
4. **Rows** live in `projection_thread_artifacts` (migration 053, repo `apps/server/src/persistence/ProjectionThreadArtifacts.ts`), keyed `(thread_id, kind, artifact_key)`. `getThreadDetailById` fans out to it and fills `OrchestrationThread.artifacts`; list snapshots deliberately leave it empty.
5. **Live updates need no extra wire message.** `packages/client-runtime/src/state/threadReducer.ts` runs the same shared extractor and `mergeArtifactRefs` over the `thread.activity-appended`, `thread.turn-diff-completed`, PR link, and `thread.artifact-*` events the client already receives. The projected table is the truth on reload; the reducer only has to converge with it.

## The counting rule

`count` is "how many tool items touched this artifact", not "how many lifecycle rows". Provenance `activityId` therefore holds the **tool call id**, not the activity id, and `mergeArtifactRefs` (client) and `ProjectionThreadArtifactRepository.merge` (SQL `ON CONFLICT`) skip the increment when `last.activityId` matches. Checkpoints use `checkpoint:<turnId>` and pull requests `pr:<key>` for the same reason: a mid-turn placeholder diff must not inflate a file's count.

Pinned and user-origin rows are never evicted or reverted away. Over `THREAD_ARTIFACT_MAX_PER_THREAD` (500) rows, the noisiest unpinned sources go first (`file-read`, then `web-search`, `url-fetch`, ...), oldest `lastSeenAt` first; the order lives in one place per side (`evictionOrder` / the `CASE` in `prune`).

## Adding a kind or a tool

1. Add the literal to `ThreadArtifactKind` and to the output or source list in `packages/contracts/src/threadArtifacts.ts`.
2. Teach `extractArtifactRefs` the tool shape (per-harness branch in `packages/shared/src/threadArtifacts.ts`) and add a fixture to its test. Adapters need no change; they already call the extractor.
3. Give the kind an eviction rank in both `evictionOrder` and the `prune` `CASE`.
4. The projector, repository, MCP tool, and reducer are kind-agnostic; the web client decides how to render it.

## Commands and events

Clients dispatch `thread.artifact.pin`, `thread.artifact.unpin`, `thread.artifact.remove` (`{threadId, kind, key}`) and `thread.artifact.add` (`{threadId, artifact: ArtifactRef}`, lands pinned with origin `user`). The decider emits `thread.artifact-pinned`, `thread.artifact-unpinned`, `thread.artifact-removed`, and `thread.artifact-added`. Artifacts are not part of the decider's read model, so pinning an unknown row is a projected no-op rather than an invariant error. Servers advertise `threadArtifacts: true` in their environment capabilities.
